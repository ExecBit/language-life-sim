# Language Life Sim — механики: реализация и приёмочные тесты

**Статус:** проектная спецификация 0.1 · **Назначение:** самостоятельные контракты реализации и проверки игровых механик пролога (P0) и остального MVP (P1). **Не** сценарий уровня, не описание художественного интерфейса и не требование создавать новый фреймворк.

**Основание:** [GAME_CONCEPT.md](GAME_CONCEPT.md) · [MVP_DESIGN.md](MVP_DESIGN.md) · [LEVEL_01.md](LEVEL_01.md) · [INTERFACE_DESIGN.md](INTERFACE_DESIGN.md) · [GAMEPLAY_TECH_REQUIREMENTS.md](GAMEPLAY_TECH_REQUIREMENTS.md).

## 1. Как использовать спецификацию

**Одна механика = одна проверяемая единица разработки.** ID неизменен и может использоваться в GitHub Issue, PR, ручном протоколе и названии теста. При разделении задачи сохранять связь с ID, а не дублировать здесь рабочие логи и чек-листы Issue.

Для каждого пункта указаны:
- **Назначение / ввод:** что делает игрок либо сценарий.
- **Контракт:** обязательный наблюдаемый результат, состояние и взаимодействие с другими механиками.
- **Границы:** важные ошибки и то, что не требуется.
- **Приёмка:** детерминированные проверки; **А** — автоматическая (unit/integration/headless), **Р** — ручная в запущенной 3D-игре. «А» не заменяет «Р» там, где оценивается читаемость действия.

**Приоритет:** P0 — необходимо для сквозного прохождения пролога; P1 — для основного life sim. P1 не должен блокировать первые P0-вертикальные срезы.

**Общие инварианты:**
1. Выбранный игроком/сценарием объект имеет устойчивый ID. Состояние не должно зависеть только от имени узла сцены.
2. У предмета в каждый момент ровно **одно** местонахождение: в мире либо у одного владельца. Промежуточная анимация не создаёт второго предмета.
3. Игровое событие завершается **один раз**; повторные клики, проигрывание анимаций и загрузка сохранения не повторяют последствия.
4. При невалидной цели, пропавшем NPC или отмене выбора игрок получает управление обратно; обязательная сцена не зависает навсегда.
5. Основная камера — **FPS**. Диалог не обязан блокировать поворот камеры и перемещение, а выбор цели явно сохраняет контекст разговора.
6. Из **коммуникативных жестов** обязательны только `point` и `nod`/`shake_head`. `take`/`give`/`place` — действия с миром. Приветственный взмах, улыбка, мимика игрока, IK и липсинк не являются критериями приёмки.

## 2. P0 — пролог

### M-01 — FPS-камера и перемещение

**Назначение / ввод:** игрок осматривает помещение и подходит к NPC/предметам обычными средствами управления.

**Контракт:** камера от первого лица; вращение взгляда и движение не требуют переключения в режим от третьего лица. В диалоге камера сохраняет ориентацию либо кратко показывает сценарное действие; при выборе цели управление взглядом и движением возвращается без потери разговора. Коллизии не позволяют проходить через стены.

**Границы:** не требуется видимое тело героя, анимация ходьбы, паркур или свободный открытый мир. Прерывание краткого постановочного ракурса не ломает событие.

**Приёмка:**
- **M01-A1 (А):** перемещение блокируется препятствием и не выводит персонажа за допустимую область.
- **M01-R1 (Р):** в комнате можно развернуться, подойти к Лене и посмотреть на предмет за её спиной.
- **M01-R2 (Р):** после возврата из выбора цели FPS-управление не заблокировано и взгляд не скачет в непредсказуемую позицию.

### M-02 — Наведение и контекстное взаимодействие

**Назначение / ввод:** игрок смотрит на доступный объект/NPC и нажимает «Взаимодействовать».

**Контракт:** доступная цель обозначается компактно; выбирается конкретный видимый объект на допустимой дистанции. У недоступного объекта нет активного действия. Отклик на наведение и нажатие виден сразу, без воспринимаемой задержки.

**Границы:** выбор через непрозрачную стену, слишком далёкой цели или скрытого объекта запрещён. Указывать сквозь другого персонажа/предмет можно только при корректной видимости целевой поверхности.

**Приёмка:**
- **M02-A1 (А):** проверка видимости и дистанции отклоняет перекрытую/далёкую цель.
- **M02-R1 (Р):** яблоко на столе выделяется при наведении; за стеной — нет.
- **M02-R2 (Р):** смена цели и клик не сопровождаются заметной секундной задержкой.

### M-03 — Контекстный диалог и немецкие ответы

**Назначение / ввод:** NPC говорит заданную реплику; игрок выбирает предложенный ответ или действие.

**Контракт:** на экране ясно указаны текущий говорящий и короткая **немецкая** реплика. Для ответа показываются только подходящие сцене варианты (обычно 2–3). Выбор создаёт событие с последствиями: `Ja` может передать чашку, `Nein` — оставить её у NPC. Без принудительного русского перевода, оценки «правильно» и обязательного ввода с клавиатуры.

**Границы:** при отсутствии доступных вариантов разговор либо продолжается NPC-репликой, либо возвращает управление; нельзя оставлять пустой заблокированный экран. Один активный интерактивный разговор одновременно достаточен.

**Приёмка:**
- **M03-A1 (А):** набор вариантов определяется состоянием сцены; недоступный ответ невозможно применить.
- **M03-A2 (А):** `Ja` и `Nein` ведут к разным разрешённым результатам.
- **M03-R1 (Р):** имя говорящего, немецкий текст и возможные ответы читаемы, не закрывают значимый предмет.

### M-04 — Разговор нескольких NPC и адресация игроку

**Назначение / ввод:** Лена говорит с Максом в присутствии игрока, затем обращается к игроку.

**Контракт:** в одном сценарном разговоре участвуют минимум два NPC и игрок; для каждой реплики известны говорящий и адресат. Пока NPC говорят друг с другом, игрок наблюдает и **не видит чужие варианты ответов**. Когда обращаются к игроку, появляется его выбор. Камера остаётся FPS, автоматические повороты не обязательны.

**Границы:** параллельные независимые беседы и автономный ИИ не нужны. Исчезновение участника обрабатывается безопасным выходом/восстановлением события.

**Приёмка:**
- **M04-A1 (А):** ответы игрока доступны лишь на адресованных ему шагах.
- **M04-R1 (Р):** «Лена → Макс → Лена → игрок» проходит без ручного переключения между NPC и без внезапного захвата камеры.

### M-05 — Выбор цели внутри разговора и указание (`point`)

**Назначение / ввод:** игрок выбирает вопрос «Was ist das?» и должен самостоятельно указать объект, например яблоко за спиной Лены.

**Контракт:** выбор реплики с неизвестной целью **не произносит её сразу**, а переводит в состояние **выбора цели**: диалоговая панель сворачивается, FPS-камера/перемещение свободны, участники и исходная реплика сохраняются. Подтверждение видимого допустимого объекта запускает короткое направленное указание (или очевидный маркер) и реплику; NPC получает `target_id` и реагирует на **выбранный объект**. После действия продолжается исходный разговор.

**Границы:** отмена возвращает к выбору реплики без последствий. Нельзя выбирать объект через стену; если он исчез или стал недоступен, игрок может выбрать другой либо отменить. Полный IK руки не требуется.

**Приёмка:**
- **M05-A1 (А):** `intent → select(target_id) → point+utterance → resume` вызывает реплику и последствия ровно один раз; при отмене — ноль раз.
- **M05-A2 (А):** перекрытая, удалённая или исчезнувшая цель не подтверждается.
- **M05-R1 (Р):** яблоко изначально за спиной NPC: игрок обходит NPC, выбирает яблоко и продолжает тот же диалог.
- **M05-R2 (Р):** NPC указывает на предмет по сценарию, и предмет действительно можно разглядеть из FPS-ракурса.

### M-06 — Подтверждение и отрицание головой (`nod`, `shake_head`)

**Назначение / ввод:** NPC говорит `Ja` / `Nein`, либо игрок выбирает соответствующий ответ.

**Контракт:** у NPC видно различимое движение головы; у игрока — короткое, умеренное движение FPS-камеры, не меняющее целевое направление надолго. Жест сопровождает реплику, а не заменяет её. Кивок и покачивание не требуют отдельной панели и не запускают повторно последствия выбора.

**Границы:** жест не прерывает взятие предмета, не меняет владение им сам по себе и не вызывает головокружительного движения камеры. Другие эмоции/жесты не обязательны.

**Приёмка:**
- **M06-A1 (А):** `Ja` связывается с `nod`, `Nein` — с `shake_head`; само событие выбора выполняется однократно.
- **M06-R1 (Р):** движения Лены/Макса различимы; короткая реакция FPS-камеры не мешает следующему наведению.

### M-07 — Взять предмет (`take`)

**Назначение / ввод:** игрок или NPC берёт указанный предмет из доступного места.

**Контракт:** предмет пропадает с исходного места и закрепляется за единственным владельцем; отображается удержание или достаточно ясная визуальная привязка к персонажу. Одна сущность/ID, без копирования. Для MVP у актёра максимум один удерживаемый предмет.

**Границы:** нельзя взять занятый, далёкий или отсутствующий предмет, а также взять второй при занятой руке. Не нужны сложная физика, инвентарь и пальцевая анимация.

**Приёмка:**
- **M07-A1 (А):** `world → held_by(actor)` меняет владельца, сохраняя один `item_id`.
- **M07-A2 (А):** повторный клик и конкурирующие попытки двух актёров не дублируют предмет.
- **M07-R1 (Р):** взять предмет из коробки понятно визуально; на исходном месте второй копии не осталось.

### M-08 — Передать предмет (`give`)

**Назначение / ввод:** игрок передаёт удерживаемый предмет Лене; NPC может передать чашку игроку.

**Контракт:** передача доступна только если отправитель владеет предметом и получатель может его принять. После подтверждения владелец один — получатель; визуально предмет оказывается у него. Сценарий ждёт завершения логического переноса, а не бесконечно ожидает анимацию.

**Границы:** повторный клик, исчезновение получателя либо отказ в момент передачи должны давать **один** согласованный результат: завершение или безопасный отказ без потери/удвоения предмета.

**Приёмка:**
- **M08-A1 (А):** `held_by(A) → held_by(B)` сохраняет единственный экземпляр.
- **M08-A2 (А):** нельзя передать чужой предмет, двум получателям одновременно или персонажу с занятым местом удержания.
- **M08-R1 (Р):** Лена получает предмет после `Gib!`; повторное нажатие не создаёт вторую передачу.

### M-09 — Положить предмет (`place`)

**Назначение / ввод:** игрок/NPC кладёт удерживаемый предмет на доступную поверхность или в заданную точку.

**Контракт:** при успешном выборе допустимой точки предмет покидает владельца и занимает место в мире. Положение выглядит правдоподобным и сохраняется. Если точка недоступна — предмет остаётся у владельца.

**Границы:** свободная физическая укладка, вращение каждого предмета и симуляция стопок не нужны.

**Приёмка:**
- **M09-A1 (А):** `held_by(actor) → world(anchor_id)` однократно обновляет местонахождение.
- **M09-A2 (А):** отказ по занятой/недоступной точке не теряет предмет.
- **M09-R1 (Р):** чашка после отказа `Nein` возвращается на стол, а не исчезает и не зависает в воздухе.

### M-10 — Подойти к объекту / точке (`approach`)

**Назначение / ввод:** герой слышит `Komm!`, подходит к Лене, затем к указанному месту или предмету.

**Контракт:** FPS-перемещение и подсказка/понятное расположение цели позволяют игроку самостоятельно дойти до доступной точки; событие продолжается после фактического достижения зоны. NPC может переместиться в заранее заданную позицию простой анимацией или переходом.

**Границы:** самостоятельный жест подзывания, сложный pathfinding, автоматическое ведение героя и физический толчок не требуются.

**Приёмка:**
- **M10-A1 (А):** вход в заданную зону активирует шаг один раз; выход и повторный вход не удваивают прогресс.
- **M10-R1 (Р):** после `Komm!` игрок понимает, куда идти, и может это сделать без телепортации через препятствие.
- **M10-R2 (Р):** если путь недоступен, сценарий не остаётся навечно в ожидании.

### M-11 — Повторить реплику или показать смысл

**Назначение / ввод:** игрок использует `Noch einmal, bitte.` или `Ich verstehe nicht.`.

**Контракт:** первая опция повторяет **ту же немецкую фразу**, не повторяя предметную передачу/предыдущие последствия. Вторая **не** просто дублирует текст: NPC указывает на предмет или демонстрирует действие, поясняя смысл без автоматического перевода. Игрок возвращается к исходному действию/ответу и может продолжить.

**Границы:** помощь не выдаёт «правильный ответ» и не блокирует ход игры при многократном вызове; частота помощи учитывается при оценке самостоятельности.

**Приёмка:**
- **M11-A1 (А):** `repeat` воспроизводит исходный `utterance_id`; его side effects не выполняются повторно.
- **M11-A2 (А):** `show` вызывает назначенный контекстный показ и отмечает помощь отдельно от самостоятельного успеха.
- **M11-R1 (Р):** демонстрация понятна из первого лица, даже если объект изначально вне обзора.

### M-12 — Сценарные события и ожидание завершения

**Назначение / ввод:** последовательность LEVEL_01 запускает реплики NPC, жесты, выборы и изменение предметов.

**Контракт:** каждому значимому шагу соответствуют устойчивый ID, условия старта, участники, ожидаемое действие и признак завершения. Следующий шаг не начинается до необходимого результата, но отсутствие анимации/невалидный объект не создаёт вечную блокировку. Сцена может давать несколько допустимых ответвлений, сходящихся дальше.

**Границы:** не нужен универсальный редактор квестов, LLM и произвольные разговоры. Сквозная логика должна быть повторно используемой, не отдельный хаотичный обработчик для каждого NPC.

**Приёмка:**
- **M12-A1 (А):** событие повторно не завершается от двойного клика, повторного вызова callback или загрузки сохранения.
- **M12-A2 (А):** `Ja` и `Nein` дают разные исходы, затем оба пути достигают следующей сцены.
- **M12-A3 (А):** потерянная цель/неудачная анимация переводят шаг в управляемое состояние восстановления.
- **M12-R1 (Р):** проход сцен A–H возможен без консольных команд и «застрявших» NPC.

### M-13 — Главное меню, настройки и пауза

**Назначение / ввод:** игрок запускает/продолжает игру, меняет настройки, ставит игру на паузу и возвращается в меню.

**Контракт:** `Новая игра`, `Продолжить` (если есть сохранение), `Настройки`, `Выход` (для настольной сборки). `Esc` в игре открывает `Продолжить / Настройки / Главное меню`. Пауза останавливает сценарные таймеры и блокирует применение игровых действий, сохраняя выбранную реплику и цель.

**Границы:** одно сохранение, без редактора персонажа/облачной синхронизации. Новая игра с существующим прогрессом требует подтверждения перезаписи.

**Приёмка:**
- **M13-A1 (А):** без сохранения нельзя вызвать `Продолжить`; наличие корректного сохранения активирует пункт.
- **M13-R1 (Р):** пауза во время выбора яблока не теряет исходный разговор; повторный Esc возвращает к тому же шагу.
- **M13-R2 (Р):** основные настройки (громкость, мышь, размер текста, окно/полный экран) применяются и не делают управление недоступным.

### M-14 — Автосохранение и восстановление P0

**Назначение / ввод:** игра автоматически сохраняет завершённые смысловые шаги; после перезапуска игрок нажимает «Продолжить».

**Контракт:** одно автоматическое сохранение в безопасных точках; сохраняются фаза, местонахождение игрока, текущий сценарный шаг/завершённые события, значимые предметы и их владельцы, учебный прогресс. При прерывании во время жеста/передачи можно восстановиться с **последней завершённой границы события**, без дублирования уже сохранённых действий.

**Границы:** не сериализовать «полупредмет» в середине анимации, не добавлять несколько слотов, cloud save или откат каждого кадра. Повреждённое/несовместимое сохранение обрабатывается с сообщением, без молчаливого затирания прогресса.

**Приёмка:**
- **M14-A1 (А):** сериализация и загрузка сохраняют один владелец/один ID на предмет и набор завершённых шагов.
- **M14-A2 (А):** повторное восстановление не удваивает события/учёт языковых единиц.
- **M14-R1 (Р):** выйти после передачи чашки → «Продолжить»: чашка там, где должна быть, сцена не переигрывается.
- **M14-R2 (Р):** выйти посреди выбора цели → «Продолжить»: восстановление на безопасном шаге, игра проходима.

## 3. P1 — основной life sim

### M-15 — Переход между локациями

**Назначение / ввод:** игрок выбирает доступное место на компактной карте/в меню перехода.

**Контракт:** минимум две функционально разные локации; переход меняет текущую локацию и согласованно переносит игрока. Доступность мест зависит от прогресса при необходимости, возврат возможен.

**Границы:** бесшовный открытый мир, транспорт и процедурная генерация не нужны.

**Приёмка:**
- **M15-A1 (А):** недоступная локация не открывается, разрешённый переход обновляет `location_id`.
- **M15-R1 (Р):** перейти A → B → A; состояние значимых предметов и задач не сбрасывается.

### M-16 — Игровое время и смена дня/ночи

**Назначение / ввод:** игрок живёт по простому игровому времени; сон/события переводят в другой период.

**Контракт:** хранить игровой день и время/период; видимое освещение соответствует периоду. Изменение времени действительно меняет доступность минимум одного NPC или действия.

**Границы:** минутная симуляция распорядка, физически точная астрономия и голод/усталость не обязательны.

**Приёмка:**
- **M16-A1 (А):** переход «вечер → сон → утро следующего дня» меняет день ровно на один.
- **M16-R1 (Р):** сцена заметно меняется; действие, доступное днём, недоступно ночью (или наоборот).

### M-17 — Доступность NPC по времени и состоянию

**Назначение / ввод:** NPC присутствует/готов общаться в определённый период либо после событий.

**Контракт:** простое правило по `npc_id`, времени и состоянию сценария; при смене периода NPC появляется в определённой точке или становится недоступным. Неактивный NPC не предлагает недействительный диалог.

**Границы:** непрерывное автономное расписание и сложная навигация NPC не нужны.

**Приёмка:**
- **M17-A1 (А):** для одного NPC как минимум два периода дают различную доступность.
- **M17-R1 (Р):** после смены времени видно различие; незавершённый разговор безопасно завершается/откладывается при смене состояния.

### M-18 — Повседневная повторяемая деятельность

**Назначение / ввод:** игрок выполняет небольшую жизненную задачу, используя знакомые реплики и предметные действия.

**Контракт:** задача имеет понятную цель, изменяет мир, может повториться в новый день с отличающимся предметом/собеседником/условием. Хотя бы одна цель требует более одной локации или общения с разными NPC.

**Границы:** не нужна экономика, система профессий и автоматическая генерация заданий.

**Приёмка:**
- **M18-A1 (А):** повторная задача на следующем игровом дне имеет отдельный экземпляр события и не дублирует предыдущий результат.
- **M18-R1 (Р):** один полный цикл действительно требует предметного действия и немецкой реплики, а повтор отличается хотя бы одним условием.

### M-19 — Языковой прогресс и контекстное повторение

**Назначение / ввод:** игра фиксирует знакомство игрока с выражением, его самостоятельное применение и применение с помощью.

**Контракт:** у учебной единицы устойчивый `unit_id`, записываются как минимум первое знакомство, попытки/успехи, контекст и факт помощи. Один и тот же ответ в другом контексте распознаётся как применение знакомой единицы; простое повторение той же сцены не считается новой успешной попыткой. Эти сведения сохраняются.

**Границы:** нет обязательного общего балла, уровня A1, SRS-алгоритма, штрафа или жёсткой блокировки за неусвоение.

**Приёмка:**
- **M19-A1 (А):** самостоятельное и подсказанное применение различаются в данных.
- **M19-A2 (А):** двойной callback не создаёт две попытки одного и того же события.
- **M19-R1 (Р):** выражение из пролога появляется в другом бытовом эпизоде без автоматической демонстрации.

### M-20 — Реальное время последней сессии и отложенная проверка

**Назначение / ввод:** игрок возвращается к игре после реального перерыва; игра проверяет перенос знакомых выражений в другую ситуацию.

**Контракт:** реальное время последней сессии хранится **отдельно** от игрового дня и не изменяется внутриигровым сном. Можно провести контрольный эпизод после возврата и отличить самостоятельное применение от подсказанного.

**Границы:** не нужна обязательная система напоминаний, произвольный SRS-алгоритм или привязка к серверному времени.

**Приёмка:**
- **M20-A1 (А):** смена игрового дня не меняет зафиксированное реальное время предыдущей сессии.
- **M20-A2 (А):** повторное прохождение после загрузки не засчитывает одну контрольную попытку дважды.
- **M20-R1 (Р):** в новом контексте игрок может применить известное выражение без принудительного повторения обучающей сцены.

## 4. Общая тестовая сцена

Чтобы не писать отдельный контент для каждой механики, использовать минимальный стенд: **одна комната и коридор**, FPS-игрок, **Лена и Макс**, стол, **яблоко** (в том числе за спиной Лены), чашка, коробка, ключи, дверь и точка перехода/сна. Предметы имеют стабильные ID; у NPC есть доступные слоты удержания.

**Обязательные интеграционные цепочки:**
1. **Разговор → выбор цели → указание → ответ**: `M01+M02+M03+M05+M12`; отмена и заслонённый объект проверяются отдельно.
2. **NPC ↔ NPC → NPC ↔ игрок → Ja/Nein**: `M03+M04+M06+M08+M12`; результат чашки зависит от ответа.
3. **Взять → передать → положить → сохранить → загрузить**: `M07+M08+M09+M12+M14`; у предмета ровно один владелец.
4. **Непонимание → повтор/демонстрация → продолжение**: `M03+M05+M11+M12`; побочные эффекты не повторяются.
5. **Смена дня → NPC/локации → повторяемая задача → языковой прогресс**: `M15+M16+M17+M18+M19+M20` (P1).

**Слой автоматических тестов:** состояние/события, доступность/проверка цели, переходы владельца, сценарные ветви, сериализация/восстановление, учёт повторных вызовов. Должен запускаться без графического интерфейса там, где это возможно.

**Слой ручных тестов:** читаемость немецких реплик, уместность указания, различимость кивка/покачивания, правильность ракурса в тесной комнате, задержка взаимодействия, возможность завершить сценарий без отладочных команд. Для проверки языковой методики нужен **отдельный playtest с новичком** — автоматический тест не доказывает понимание немецкого.

## 5. Порядок реализации и критерии завершения PR

**Рекомендуемый порядок минимальных срезов:** `M01–M02` → `M07–M09` → `M03–M04` → `M05–M06` → `M11–M12` → `M13–M14`, после чего интеграционный прогон LEVEL_01. Для P1: `M15–M17` → `M18–M20`. Зависимости локальных задач допустимо менять, если конечные контракты не нарушены.

Задача считается готовой к Review, если:
- реализован публично наблюдаемый результат механики, **а не только интерфейс/пустой обработчик**;
- перечислены пройденные `Mxx-A*` с командами запуска и результаты `Mxx-R*` с коротким описанием того, что было видно в игре;
- существуют проверяемые автоматические тесты для состояния/правил, если механика подразумевает такие правила;
- проверены как минимум **успешный путь, отмена/ошибка и повторное применение**; в PR указаны реально не проверенные случаи;
- не добавлены обязательные функции за пределами P0/P1 или новые жесты без изменения дизайн-документов.

**Граница ответственности:** этот файл фиксирует **как работает и как тестируется** механика; `LEVEL_01.md` — **где именно и зачем** она применяется; `INTERFACE_DESIGN.md` — **как это выглядит для игрока**; `GAMEPLAY_TECH_REQUIREMENTS.md` — **минимальный общий технический контракт**.
