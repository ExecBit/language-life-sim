# Language Parser — техническая спецификация гибридного парсера

**Статус:** контракт реализации экспериментальной коммуникации. **Приоритет:** этот документ конкретизирует парсер для [эксперимента «Закрытая комната»](COMMUNICATION_EXPERIMENT.md); при расхождении примеров разбора использовать правила здесь, а игровые предусловия и сюжет — из документа эксперимента. Не является спецификацией полного немецкого NLP.

## 1. Цель и принцип работы

Игрок самостоятельно собирает короткую немецкую реплику из доступных слов. Система должна распознать **смысл в ограниченной предметной области**, а не сравнить текст с эталонной фразой. Грамматические ошибки и эллипсис допускаются, когда остаётся однозначная интерпретация. Парсер **не решает**, можно ли отдать ключ или открыть дверь: это отдельная проверка состояния мира.

Конвейер:

```text
Word catalog (lemma + surface forms + features)
  → input tokens
  → lexical analysis (all candidate readings)
  → shallow syntax / clause and scope detection
  → semantic frame (who, wants/has/can, action, object, polarity, question)
  → intent mapping
  → recognized | clarify | unsupported | unknown
  → world resolver (separate component)
  → scripted NPC reaction (separate component)
```

**Запрещённые сокращения:** глобальная блокировка по отдельному слову (например, `will`); глобальный поиск `nicht` без определения области отрицания; `if text == "Ich brauche den Schlüssel"`; выполнение действия только по совпадению слова `öffnen`; превращение сообщения о проблеме в прямую просьбу; автоматическое игнорирование незнакомых смысловых слов; «уверенность» на основе произвольного порога без тестов.

## 2. Разделение ответственности и минимальные интерфейсы

Реализация может использовать GDScript-классы/ресурсы/словари, соответствующие контрактам, без нового универсального фреймворка.

### 2.1. Word Catalog / Morphology

Каждая лексическая запись хранит:
- `lemma_id` — стабильный идентификатор леммы;
- `surface` — вводимую форму (включая заглавные буквы/умлауты);
- `pos` — часть речи;
- `features` — нужные для разбора грамматические признаки (лицо, число, падеж, отрицание, тип местоимения, модальность), если применимо;
- `semantic_id` — нормализованное значение (`key`, `door`, `want`, `open`);
- `availability` — доступность игроку (не обязательно то же самое, что распознавание парсером).

**Автодополнение и парсер используют один источник лексических данных.** Все разрешённые в эксперименте формы должны быть доступны для набора по префиксу, включая `will`, `brauche`, `keinen`, `mir`, `dir`, `kannst`, `öffne`, `zu`. Если форма распознаётся парсером, но отсутствует в каталоге ввода, это дефект согласованности; если игрок вводит произвольный текст вне каталога, парсер всё равно должен вернуть контролируемый результат.

Не смешивать лемму и словоформу: `will` — форма `wollen` (1-е/3-е лицо единственного числа), а не запрещённое слово; `willst`, `wollen` — другие формы. `kein`, `keinen`, `keine` — варианты отрицательного определителя. `Schlüssel` — существительное, регистр сохраняется в отображении, сравнение регистронезависимое.

### 2.2. Parse Result

Контракт результата (схема, не требование точного API):

```text
{
  status: RECOGNIZED | NEEDS_CLARIFICATION | UNSUPPORTED | UNKNOWN,
  intent: REQUEST_ITEM | REQUEST_HELP | ASK_LOCATION | ASK_REASON |
          ASK_PERMISSION | REPORT_PROBLEM | ACCEPT | REFUSE |
          REQUEST_ACTION | PROHIBIT_ACTION | null,
  frame: {
    speaker: player,
    subject: player | anna | other | unresolved,
    addressee: anna | other | unresolved,
    predicate: want | need | have | can | open | help | give | be | ...,
    action: open | give | help | null,
    object_id: key | door | room | ... | null,
    polarity: positive | negative | unresolved,
    modality: want | need | can | none,
    speech_act: statement | question | request | prohibition | unresolved,
    target_id: optional stable world object reference
  },
  ambiguity: [reason codes],
  unsupported_features: [feature codes],
  diagnostics: [non-blocking error codes],
  normalized_tokens: [...]
}
```

Семантический `frame` должен оставаться доступен даже при `UNSUPPORTED` или `NEEDS_CLARIFICATION`, если частично определён; downstream не выполняет действие, если статус не `RECOGNIZED`. Не использовать произвольное числовое `confidence` как разрешение действовать. Предпочесть явные причины неоднозначности.

### 2.3. World Resolver / NPC

На вход получает `RECOGNIZED` и проверяет `actor`, `target_id`, владельца предмета, доступность/знания NPC, разрешение, замок, текущий pending question. Возвращает `action`, `clarification`, `refusal` или `information`; **не изменяет исходный смысл фразы**. Одни и те же `frame` + состояние мира дают одинаковый результат. Уточнение и непонимание не изменяют мир.

## 3. Лексические классы и минимальная грамматика

Минимум для среза (реальный набор форм определяется совместно с UI; все нижеупомянутые тестовые слова должны быть распознаваемы):

| Класс | Примеры | Назначение |
| --- | --- | --- |
| Местоимения | `ich`, `du`, `mir`, `dir`, `Anna` | Кто действует, к кому обращаются |
| Модальные/потребность | `will`, `willst`, `brauche`, `brauchen`, `kann`, `kannst` | Желание, потребность, возможность |
| Действия | `öffnen`, `öffne`, `geben`, `gib`, `helfen`, `hilf` | Целевое действие |
| Обладание/состояние | `habe`, `hat`, `ist` | Сообщение о состоянии |
| Вопросительные | `wo`, `warum`, `was` | Тип вопроса |
| Отрицание | `nicht`, `kein`, `keinen`, `keine` | Отрицание действия/обладания/предмета |
| Предметы | `Schlüssel`, `Tür`, `Zimmer` | Объекты и места |
| Служебные | `der`, `die`, `den`, `das`, `ein`, `eine`, `bitte`, `zu` | Грамматика/вежливость |
| Ответы | `ja`, `nein`, `danke` | Короткие реакции |

Поддерживаемые **структурные семейства**, а не полные строковые шаблоны:
1. **Желание/потребность:** `[ich] (will|brauche) [артикль] OBJECT [bitte]` → `REQUEST_ITEM` при положительной полярности и контексте обращения к NPC. `Ich will Schlüssel` → `REQUEST_ITEM(key)`, диагностировать пропущенный артикль, **не** `UNKNOWN`. `Ich will den Schlüssel` и `Schlüssel, bitte` — тот же смысл. Вопрос/отрицание изменяют интерпретацию.
2. **Нужное действие:** `[ich] will OBJECT öffnen` / `[ich] möchte OBJECT öffnen` (если `möchte` доступно) → желание открыть, не команда Анне открыть. Если игрок просит Анну открыть: `Kannst du die Tür öffnen?` / `Öffne die Tür, bitte` → `REQUEST_ACTION(open, door)`. Указывать, кто предполагаемый исполнитель.
3. **Проблема:** `ich habe keinen OBJECT` → `REPORT_PROBLEM(missing, object)`; `ich kann OBJECT nicht öffnen` → `REPORT_PROBLEM(cannot_open, object)`. **Не** превращать в `REQUEST_ITEM` или `REQUEST_ACTION` без уточнения.
4. **Информационные вопросы:** `Wo [ist] [артикль] OBJECT?` → `ASK_LOCATION`; `Warum ist die Tür zu?` → `ASK_REASON`; `Was ist das?` с указанием → запрос идентификации (переиспользовать существующий механизм).
5. **Помощь:** `Kannst du mir helfen?` / `Hilf mir bitte` / `Helfen bitte` → `REQUEST_HELP`; при неизвестной цели NPC уточняет, а не открывает дверь по умолчанию.
6. **Разрешение:** `Kann ich [артикль] OBJECT öffnen?` → `ASK_PERMISSION` (вопрос о возможности/разрешении в контексте комнаты; не команда открыть).
7. **Ответы:** `Ja`, `Nein` → `ACCEPT` / `REFUSE` только при активном предложении или уточнении; вне такого контекста `NEEDS_CLARIFICATION` или социальная реакция без действия.
8. **Запрет:** `Öffne die Tür nicht` → `PROHIBIT_ACTION(open, door)` либо безопасное `UNSUPPORTED`, но **никогда** `REQUEST_ACTION(open, door)`.

Не нужно поддерживать придаточные предложения (`dass`, `weil`), произвольные времена, все падежи и всю морфологию немецкого. Если предложение содержит неподдерживаемую структуру, но также знакомые слова, не извлекать из него «удобный» императив.

## 4. Алгоритм разбора (нормативный порядок)

1. **Токенизация.** Unicode, пробелы, знаки препинания, `?` как дополнительный сигнал, не обязательное условие вопроса; регистр не влияет на lookup. Не удалять `nicht`, `kein`, местоимения, модальные глаголы или неизвестные слова.
2. **Лексический разбор.** Каждому токену сопоставить все возможные леммы и признаки; незнакомый токен оставить `UNKNOWN_TOKEN` с позицией. Не удалять его молча.
3. **Границы конструкции.** Выделить простую главную клаузу, вопросительное начало, явный императив, маркеры вежливости; определить потенциального субъекта и адресата. Для `ich` субъект — игрок; для `Anna` субъект — Анна, если она грамматически субъект, а не обращение. Контекст текущего собеседника можно использовать как адресата, **не** для подмены явного субъекта.
4. **Связи предикатов.** Модальный глагол связывать с инфинитивом/предметом, а не интерпретировать отдельно. `will Schlüssel` → желание обладать ключом; `will Tür öffnen` → желание открыть дверь. `kannst ... öffnen` → вопрос о действии собеседника. Наличие слова `will` само по себе не блокирует фразу.
5. **Отрицание и область действия.** `kein/keinen` отрицает соответствующую именную группу; `nicht` относится к связанному предикату/действию, если связь однозначна. `ich will nicht öffnen` = игрок не хочет открывать; `öffne nicht` = запрет. Если scope неясен, `NEEDS_CLARIFICATION`, не удалять отрицание и не выполнять действие.
6. **Нормализация ошибок.** Разрешить отсутствие артикля, ошибочный артикль/падеж, несогласованную форму глагола при ясном субъекте, отсутствие вспомогательного `ist` в коротком вопросе, короткие телеграфные просьбы. Сохранить диагностику `OMITTED_ARTICLE`, `AGREEMENT_MISMATCH` и т. п.; не исправлять отрицание, субъект, основной глагол, вопросительность и тип речевого акта догадкой.
7. **Семантический frame.** Составить субъект/модальность/действие/объект/полярность/речевой акт. Для `Schlüssel?` не предполагать просьбу автоматически, если возможен вопрос о местоположении; вернуть `NEEDS_CLARIFICATION`.
8. **Сопоставление намерения.** Только после анализа структуры: просьба о предмете ≠ сообщение об отсутствии ≠ вопрос о местоположении ≠ желание самому открыть ≠ просьба NPC открыть.
9. **Разрешение неоднозначности.** Если несколько интерпретаций различаются игровым действием, запрашивать уточнение; при неизвестном критическом слове или неподдерживаемой клаузе возвращать `UNKNOWN/UNSUPPORTED`. Контекст может разрешить **референцию** (`das` + указанный объект), но не инвертировать полярность или речевой акт.
10. **Мир и реакция.** Только после успешного разбора world resolver выбирает результат. Повторная отправка не должна дублировать действия.

### Порядок правил и конфликты

Нельзя полагаться на порядок `if`-веток для случайного выбора намерения. Приоритет: (а) явная структура вопроса/запрета/отрицания; (б) связанный предикат и субъект; (в) предмет/цель; (г) вежливость и контекст. При конфликте двух семантически разных распознаваний → `NEEDS_CLARIFICATION`. Более короткий матч не должен побеждать более полный, если пропускает отрицание или модальный глагол.

## 5. Строгие правила безопасного восстановления смысла

**Допустимо восстанавливать:** отсутствующий артикль (`ich will Schlüssel`), неверное согласование (`ich brauchen Schlüssel`), телеграфную просьбу (`Schlüssel bitte`), пропущенное `ist` в `Wo Schlüssel?`.

**Недопустимо домысливать:** кто совершает действие, если это меняет результат; наличие/отсутствие отрицания; что вопрос является командой; что у Анны есть ключ; что игрок имеет разрешение; что `ich habe keinen Schlüssel` означает «отдай ключ»; что любое упоминание двери означает «открой».

Если фраза грамматически ошибочна, но смысл один, вернуть `RECOGNIZED` + диагностическое замечание. Если возможны разные последствия, вернуть `NEEDS_CLARIFICATION` с вариантами **смысла** (например, «Где ключ?» / «Дать ключ?»), а не списком готовых правильных немецких фраз. Уточнение не должно выдавать ключ или открывать дверь.

## 6. Минимальная матрица обязательных тестов

Для всех случаев тестировать `status`, `intent`, `frame` (субъект, объект, полярность, речевой акт) и **отсутствие нежелательных игровых эффектов**.

| Ввод | Ожидаемый разбор / результат |
| --- | --- |
| `Ich will Schlüssel` | `RECOGNIZED REQUEST_ITEM(key)`, отсутствие артикля допустимо |
| `Ich will den Schlüssel` | `RECOGNIZED REQUEST_ITEM(key)` |
| `Ich brauche Schlüssel` | `RECOGNIZED REQUEST_ITEM(key)` |
| `Ich brauchen Schlüssel` | `RECOGNIZED REQUEST_ITEM(key)` + ошибка согласования |
| `Schlüssel bitte` | `RECOGNIZED REQUEST_ITEM(key)` в диалоге с Анной |
| `Schlüssel?` | `NEEDS_CLARIFICATION`, без передачи |
| `Wo ist der Schlüssel?` | `RECOGNIZED ASK_LOCATION(key)` |
| `Wo Schlüssel?` | `RECOGNIZED ASK_LOCATION(key)` |
| `Ich habe keinen Schlüssel` | `RECOGNIZED REPORT_PROBLEM(missing(key), subject=player)` |
| `Anna hat keinen Schlüssel` | Сообщение об отсутствии ключа **у Анны**, не у игрока |
| `Ich kann die Tür nicht öffnen` | `REPORT_PROBLEM(cannot_open(door), negative)` |
| `Ich will die Tür öffnen` | Желание **игрока** открыть дверь, не команда Анне |
| `Kannst du die Tür öffnen?` | `REQUEST_ACTION(open,door,actor=anna)` |
| `Kann ich die Tür öffnen?` | `ASK_PERMISSION(open,door,actor=player)` |
| `Öffne die Tür bitte` | `REQUEST_ACTION(open,door,actor=anna)` |
| `Öffne die Tür nicht` | `PROHIBIT_ACTION` или `UNSUPPORTED`; дверь не открывается |
| `Ich will nicht öffnen` | Отрицательное желание, **не** просьба открыть |
| `Ich will nicht, dass Anna die Tür öffnet` | `UNSUPPORTED` (сложная клауза), **без открытия** |
| `Kannst du mir helfen?` | `REQUEST_HELP` без автоматического открытия |
| `Helfen bitte` | `REQUEST_HELP` |
| `Warum ist die Tür zu?` | `ASK_REASON(door)` |
| `Ja` / `Nein` | Соответствующий ответ только при активном предложении |
| `Das öffnen` + pointed door | Допустимо уточнение или разбор цели `door`, **не** безусловная команда |
| `Das öffnen` без target | `NEEDS_CLARIFICATION` |
| Неизвестное содержательное слово | `UNKNOWN` или `UNSUPPORTED`, без действия |
| `will` отдельно | `NEEDS_CLARIFICATION` / `UNKNOWN`, не глобальный запрет |
| `Ich will Schlüssel nicht` | Отрицательное желание/неоднозначность, **не** `REQUEST_ITEM` |

Обязательны также **метаморфные тесты**: добавление `bitte`, замена допустимого артикля или удаление артикля не меняют базовое намерение; замена `ich` на `Anna` меняет субъект; добавление `nicht` не может сохранить положительное действие; замена `Schlüssel` на другой зарегистрированный предмет меняет `object_id` без нового полного строкового шаблона. Неизвестное слово в позиции объекта не должно наследовать объект предыдущего высказывания.

**Интеграционные сценарии:**
- Ключ у Анны, Анна свободна: просьба о ключе → передача ровно одного ключа.
- Ключ не у Анны: та же фраза → нет передачи, корректный отказ/информация.
- Анна занята: просьба → нет передачи, ответ о занятости.
- Анна не знает местоположения: `Wo ist der Schlüssel?` → честное непонимание местоположения, не выдуманное указание.
- Запрет/отрицание/неизвестная фраза → дверь остаётся закрытой.
- Уточнение после `Schlüssel?` сохраняет контекст, но не создаёт действия до однозначного ответа.
- Перезапуск/повторный callback не удваивает ключ и событие.
- Все доступные в UI словоформы парсятся или дают явно задокументированный `UNSUPPORTED`; тест отдельно проверяет присутствие `will` в автодополнении.

## 7. Стратегия реализации и критерии завершения

1. Проверить существующие диалоговые компоненты и словарь; адаптировать минимально. Не добавлять отдельную NLP-библиотеку без доказанной необходимости.
2. Вынести лексикон и словоформы в единый источник для UI и парсера.
3. Реализовать нормализацию, морфологические признаки, структурные правила и семантические frame как **чистую логику**, тестируемую без 3D-сцены.
4. Отдельно реализовать world resolver и сценарные ответы NPC.
5. Запустить табличные unit-тесты из раздела 6, метаморфные и интеграционные тесты.
6. Пройти вручную оба способа открытия комнаты, информационный путь и отрицательные случаи в Godot.
7. В PR приложить команды запуска тестов, их результаты, таблицу поддерживаемых/неподдерживаемых конструкций и честные ограничения.

**Готово**, когда все обязательные тесты проходят и игрок может набрать `ich will Schlüssel` через автодополнение и получить осмысленную контекстную реакцию (передачу ключа при допустимом состоянии либо объяснение отказа), не нарушая обработку отрицания. Нельзя объявлять задачу завершённой после добавления одного исключения для `will`.

## 8. За пределами контракта

Не реализовывать произвольную свободную речь, все формы немецкого, придаточные предложения, исправление произношения, LLM/NLU-модель, генерацию реплик, синтаксические деревья общего назначения, обучение по статистике и все языки мира. Расширение словаря должно быть **данными**, а добавление нового семейства грамматических конструкций — отдельным осознанным изменением правил с тестами.


## 9. Обязательный регрессионный прогон игровой сцены

Этот раздел дополняет unit-матрицу раздела 6: агент обязан **прогнать тесты парсера и игрового контекста**, а не ограничиться проверкой `Ich will Schlüssel`. Если автоматизация полного 3D-прохода невозможна, выполнить доступные headless/unit/integration тесты и отдельно перечислить ручные действия и непроверенные пункты. Не отмечать ручной сценарий как пройденный без реального запуска.

**Исходное состояние по умолчанию:** игрок перед закрытой дверью; Анна рядом и доступна; ключ у Анны, если не указано иное. Перед независимыми сценариями сбрасывать состояние. Сохранять различие между *распознанным намерением*, *ответом NPC* и *фактическим изменением мира*.

| ID | Реплика / действие | Ожидаемый результат |
| --- | --- | --- |
| R01 | `Ich will Schlüssel` | `REQUEST_ITEM(key)`; Анна отдаёт ключ, если может |
| R02 | `Ich brauche den Schlüssel`, `Schlüssel bitte` | Тот же intent, без дополнительных полнострочных исключений |
| R03 | `Wo ist der Schlüssel?` | `ASK_LOCATION(key)`; Анна сообщает известное местоположение, **не** отдаёт ключ автоматически |
| R04 | `Ich habe keinen Schlüssel` | `REPORT_PROBLEM(missing(key))`; помощь/уточнение, не безусловная передача |
| R05 | `Kannst du mir helfen?` | `REQUEST_HELP`; Анна уточняет цель или предлагает доступную помощь, не открывает дверь без определённой цели |
| R06 | `Kannst du die Tür öffnen?` | `REQUEST_ACTION(open,door,actor=anna)`; при доступе Анны дверь может быть открыта ею; второй путь решения |
| R07 | `Warum ist die Tür zu?` | `ASK_REASON(door)`; ответ только на основании известной причины, без открытия |
| R08 | `Kann ich die Tür öffnen?` | `ASK_PERMISSION(open,door,actor=player)`; ответ о разрешении, **не** действие Анны |
| R09 | `Schlüssel?` | `NEEDS_CLARIFICATION`; ни ключ, ни дверь не изменяются; продолжение разговора доступно |
| R10 | `Ich brauchen Schlüssel` | Ошибка согласования допускается; `REQUEST_ITEM(key)` с диагностикой |
| R11 | `Öffne die Tür nicht` | Запрет или `UNSUPPORTED`; **дверь остаётся закрытой** |
| R12 | `Ich will nicht öffnen` | Отрицательное желание; не превращается в команду открыть |
| R13 | `Anna hat keinen Schlüssel` | Субъект — Анна, не игрок; не интерпретировать как просьбу |
| R14 | `Ich will nicht, dass Anna die Tür öffnet` | `UNSUPPORTED`; сложная конструкция не должна открывать дверь |
| R15 | Неведомое содержательное слово или неоднозначная ссылка | Безопасное непонимание/уточнение, без изменения мира |

### Контекстная матрица (одна реплика, разные состояния)

Для `Ich brauche den Schlüssel` проверить **три отдельных прогона**:
- **W01:** ключ у свободной Анны → передача ровно одного ключа.
- **W02:** ключ в другом месте → Анна не передаёт несуществующий у неё предмет, сообщает об отсутствии; при известном местоположении может подсказать.
- **W03:** Анна занята → отказ или просьба подождать, без передачи.

Для `Wo ist der Schlüssel?`:
- **W04:** Анна знает местоположение → сообщает корректное известное место.
- **W05:** Анна не знает → честно сообщает о незнании, не выдаёт выдуманное место.

Для `Kannst du die Tür öffnen?`:
- **W06:** у Анны есть ключ/доступ и она свободна → допустимое открытие.
- **W07:** доступа нет или она занята → дверь остаётся закрытой, объяснение/уточнение.

### Требования к выполнению

1. Unit-тесты должны проверять `status`, `intent`, `frame`, субъект, отрицание, объект и тип речевого акта. Интеграционные тесты должны проверять фактическое состояние двери/ключа и отсутствие дубликатов.
2. Для R01–R15 и W01–W07 предусмотреть автоматический регрессионный прогон, где позволяет текущая архитектура. Не добавлять отдельную игровую систему ради тестов.
3. Проверить в запущенном Godot UI-сборку слов через префикс/Enter, возможность исправить фразу, отправку, возврат FPS-управления и оба пути достижения комнаты (получить ключ самому / попросить Анну открыть).
4. После уточнения `Schlüssel?` продолжение должно сохранять контекст, но не выполнять действие преждевременно.
5. Для каждого сценария зафиксировать `PASS/FAIL/NOT_RUN`, при `FAIL` — фактическое поведение, при `NOT_RUN` — причину и способ ручной проверки. В PR дать команды запуска тестов и итоговую сводку, **не заявлять о прохождении непроверенных сценариев**.
6. Проверить, что изменения не сломали существующие уровни 01–02 и их диалоговые взаимодействия.

Это **обязательный регрессионный набор** для экспериментальной механики, а не требование создавать новый уровень или переписывать весь NLP.
