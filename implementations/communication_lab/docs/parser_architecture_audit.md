# Аудит понимания реплик Communication Lab

Исследовано состояние `1355f7a9826a3c47ff2c2ef35b24c1837aef171c`, Godot 4.7.1. Это расследование, не исправление production-парсера. Диагностические прогоны используют исходный проект; экспорта, установки библиотек, запуска моделей и изменения корпуса не было. Отложенные 50 validation cases не запускались и не использовались для подбора правил.

## Вывод

Ограниченный словарь и 19 действий позволяют построить значительно более устойчивый разговорный интерфейс. Но словарь сам по себе не задаёт ни грамматику, ни смысл, ни разрешение пропусков из контекста. Текущий RPG-разбор в основном ищет присутствие слов и возвращает первую подходящую ветвь. Восстановления произвольного пропущенного аргумента и выбора между несколькими интерпретациями там нет. Добавление ещё одной формы слова не исправляет этот механизм.

Нужны единый семантический анализатор, частичные смысловые структуры, типизированный разговорный контекст и уточнения по недостающему полю. Простое сопоставление со списком сгенерированных предложений недостаточно: отрицание и перестановка участников могут давать очень похожие строки с противоположным смыслом.

## Проверенные причины

| Причина | Доказательство в текущем коде | Последствие |
| --- | --- | --- |
| Несколько расходящихся анализаторов | `lab_session.gd:64` вызывает только `DialogueLanguage.analyze_rpg`. `test_issue65.gd` в основном вызывает `Grammar.parse` из `dialogue_resolver.gd`. Старый corpus runner `_evaluate` тоже использует resolver/parser и удалённые методы Session. | Улучшение старого resolver и зелёный unit-тест не обеспечивают это же поведение в живой сцене. |
| Порядок keyword-ветвей определяет смысл | `dialogue_language.gd:82–93`: положительное `bekommen` с `ich` сначала становится REPORT_HAS_CARD; вопросительная ветвь ниже уже недостижима для этого ввода. | Даже правильный `Kann ich einen Pass bekommen?` получает неверный речевой акт. |
| Отрицание не связано с предикатом | В начале `analyze_rpg` один флаг ищет `nicht/kein/...`; `nein` внутри фразы не учитывается. В ветвях помощи полярность затем явно устанавливается в positive. | Отказ может стать положительным предложением; самопоправка — ложным повторным заявлением. |
| Пропущенное слово не представлено как недостающее поле | Просьба о пропуске разбирается только внутри ветви с явным `karte/pass`. В custom lexical readings `features` пусты; у `vorläufigen` нет связи с типом обсуждаемого документа. | `Ich möchte einen vorläufigen` возвращает UNKNOWN вместо кандидата с пропущенным объектом. |
| Контекст — преимущественно pending yes/no | `pending_proposition` берётся из авторского `open_proposition`. В G70 нет такого вопроса, хотя NPC оспаривает роль игрока. | `Nein` не к чему привязать. Нет общего представления обсуждаемой пропозиции, референтов и отсутствующих аргументов. |
| «Полнота смысла» не проверяется | `_rpg_recognized` безусловно присваивает `semantic_recovery_status = COMPLETE`, хотя ряд полей остаётся unresolved и остаток известных слов не проверен. | F2 может создавать ложное впечатление надёжного полного анализа. |
| Подсказка не строится из частичного смысла | Session умеет подтвердить уже выбранное ребро при несовпадении с меню; для остальных неудач `_failure_reply` обычно возвращает общую просьбу переформулировать. | Даже полезная частичная информация не превращается в короткий адресный вопрос NPC. |
| Покрытие слов не равно покрытию смысла | `vocabulary`/`search_words` обеспечивают F1 и поиск, но не задают валентность, роли, область отрицания или допустимый эллипсис. | Наличие всех слов в памятке не означает понимание их новых сочетаний. |

Фиксация истории: старый подход с `DialogueLanguage.analyze` и fallback на `DialogueGrammar.parse` виден в коммите `e9b1365`; отдельный RPG entry point появился в `b961210`. Сохранение старых файлов и тестов не сохранило старый механизм в новом runtime-пути.

## Что воспроизведено

Диагностический драйвер: [experiments/audit_runtime_parser.gd](../experiments/audit_runtime_parser.gd). Он создаёт контексты через реальные ходы Session, перед каждой пробой создаёт свежую сессию, записывает фактическое принятие выбора меню, смысловую структуру и последствия. 33 наблюдения: 27 вызовов Session и 6 сравнений resolver/runtime. Это специально выбранные диагностические контрасты, **не независимая выборка и не процент качества**. Полные результаты: ignored `.local/parser-audit-results.json`.

| Ввод и контекст | Фактическое поведение |
| --- | --- |
| `Ich möchte einen Pass.` в G40 | REQUEST_PASS; переход G50. |
| `Ich möchte einen vorläufigen Pass.` в G40 | REQUEST_PASS; переход G50. |
| `Kann ich einen Pass bekommen?` в G40 | REPORT_HAS_CARD, speech_act=statement; перехода нет. |
| `Ich möchte vorläufigen`, `Ich möchte einen vorläufigen.`, `Einen vorläufigen, bitte.` в G40 | Все UNKNOWN/NO_SUPPORTED_INTENT; ни одного конкретного уточнения объекта. |
| `Ich möchte keinen Pass.` | REPORT_NO_CARD — нежелание получить ошибочно превращается в отсутствие карты. |
| `Darf ich einen Pass bekommen?` | UNKNOWN_TOKEN, хотя код вопросительной ветви проверяет `darf`. Лексикон и правила рассогласованы. |
| `Ich bin Techniker nein`, `Ich bin nein Techniker`, `Ich bin Techniker, nein.` в G70 с выбранным claim_technician | Все CLAIM_TECHNICIAN/positive/COMPLETE; реальный переход G80 и эффект trust=suspicious. |
| `Nein` в G70 | NEEDS_CLARIFICATION/NO_OPEN_YES_NO_TARGET; нет конкретного «Du bist also kein Techniker?». |
| `Ich kann dir nicht helfen.` | Старый resolver: PLAYER_CANNOT_HELP/negative. Runtime: OFFER_HELP/positive. У этого графа нет ребра помощи, поэтому здесь эффекта нет; смысловой дефект уже есть. |
| `Ich bin Techniker, aber ich bin kein Techniker.` | DENY_TECHNICIAN/COMPLETE, противоречие не сохраняется как неоднозначность. |
| `Ich bin Techniker blorple` | UNKNOWN_TOKEN, эффекта нет: защита от действительно неизвестного слова работает. |

Обнаружена и проблема материала F1: конструкция `Kannst du Tom eine Nachricht geben?` помечена как «согласиться передать сообщение», хотя вопрос адресован собеседнику: «Можешь ты передать Тому сообщение?». Наличие перевода и всех слов не проверяет корректность участника действия. В текущем G100 эта фраза получает UNKNOWN. Материал в рамках расследования не исправлялся.

## Как должен работать один механизм

1. **Лексический анализ с альтернативами.** Лемма, словоформа, грамматические признаки, семантический тип, источник исправления. Опечатка может дать несколько чтений. Например, `mochte` — настоящее немецкое слово с другим значением; превращать его в `möchte` без контекста и пометки нельзя.
2. **Композиционный разбор.** Строить значения из типов конструкций: сообщение о владении, желание/просьба получить, заявление о роли, передача сообщения, ответ. Сохранять actor, recipient, object, modality, polarity и speech act. Проверять, куда отнесён каждый значимый фрагмент ввода.
3. **Ограниченные восстановления.** Пропуск артикля, ошибочное согласование, пропущенная связка и отсутствующий аргумент — разные операции с явным происхождением. Нельзя «чинить» отрицание в положительный смысл или выбрасывать условие ради удобного перехода.
4. **Контекст обсуждения.** Хранить обсуждаемый вопрос/утверждение, его тип, доступные референты и ход-источник. Подбор кандидатов использует меню как мягкую подсказку. Явные слова игрока имеют приоритет; доступность удачного игрового ребра не доказывает намерение.
5. **Кандидаты и проверка полноты.** Ноль кандидатов — адресное объяснение неизвестного/неподдерживаемого. Один непротиворечивый полный смысл — передать графу. Несколько смыслов либо критический вывод из контекста — конкретное уточнение. Ранг кандидата не выдавать за статистический процент уверенности.
6. **Уточнение из недостающего поля.** `Einen vorläufigen Pass?`, `Du bist also kein Techniker?`, `Soll ich helfen, oder hilfst du?` — разные виды вопросов, а не один fallback. Ответ Ja/Nein относится к сохранённой пропозиции и ходу; новая содержательная реплика, отказ и reset управляют её жизненным циклом. Эффект выполняется один раз после разрешения.
7. **Отдельный слой действий.** Существующие guards/effects графа остаются последним фильтром. Неясный разбор не меняет доступ, доверие или обещание; выяснение смысла не равно штрафу за язык.

Для `Ich möchte vorläufigen` в G40 можно получить частичный смысл «игрок хочет получить объект с признаком temporary». Обсуждаемый Pass подходит по типу; NPC предлагает подтвердить его. В другом контексте тот же эллипсис не обязан означать Pass. Для `Ich möchte keinen Pass` явное отрицание желания не превращается в отсутствие документа. Для `Kannst du ... geben?` нельзя менять исполнителя с NPC на игрока, чтобы попасть в доступный ACCEPT_MESSAGE.

Правильные формы NPC желательно генерировать из той же семантической модели и морфологии. У каждой подсказки тогда проверяются роли и формы, а F1 получает нужные словоформы. Полная готовая реплика не должна быть обязательным первым ответом на затруднение: сначала можно дать короткое подтверждение предмета или вопрос о недостающей роли.

## Готовые подходы и их границы

| Подход | Практический вывод для лаборатории |
| --- | --- |
| Typed semantic grammar + контекст + ограниченный repair | Предпочтительная архитектура для этого домена: значения и конструкции комбинируются, ошибки формы отделены от неопределённого смысла. Это правила семейств, не готовых строк. Сам engine ещё нужно реализовать или интегрировать и проверить. |
| Генерация допустимых реплик и близость строк | Полезна для предложения кандидатов и тестов. Не должна единолично выбирать действие: `kein`, `nicht`, `ich/du`, `mir/dir` меняют смысл при минимальном изменении строки. |
| GF / German Resource Grammar Library | Реальный готовый ресурс морфологии и синтаксиса, разбор и генерация по семантической грамматике. Подходит для прототипирования корректных вариантов и подсказок. Не является готовым терпимым парсером ошибочного немецкого новичка; для неполных фраз нужен слой восстановления/контекста, для Godot — проверенная интеграция. Ничего не установлено и не измерено здесь. |
| spaCy / dependency parser | Может дать леммы, морфологию и синтаксические зависимости. Из этих аннотаций ещё нужно получить игровые намерения и контекстные пропуски. Установка модели сама по себе не решает наш контракт; качество на таком вводе требует отдельной проверки. |
| LLM с ограниченной схемой результата | Возможный альтернативный источник кандидатов. Формально корректный JSON не гарантирует правильных ролей/отрицания. Нужны те же независимые тесты и граница исполнения; также появляются модель, задержка, стоимость и воспроизводимость. Без сравнительного эксперимента это не доказанное улучшение. |

Основания: классическая task-oriented система CMU использовала гибкий frame-based разбор и историю диалога для неполных высказываний ([Issar & Ward, 1993](https://www.isca-archive.org/eurospeech_1993/issar93_eurospeech.html)). Работа [Ginzburg & Cooper, 2001](https://aclanthology.org/P01-1031/) рассматривает разрешение эллипсиса через грамматику и информационное состояние диалога. Это подтверждает осуществимость подхода, но не переносимость опубликованных процентов на нашу игру.

[GF RGL](https://www.grammaticalframework.org/lib/doc/rgl-tutorial/index.html) разделяет абстрактный смысл и языковую реализацию. [Документация о расширении GF](https://www.grammaticalframework.org/lib/doc/translation.html) отдельно обсуждает ограничения и robust processing: наличие грамматики не равно пониманию любого ошибочного ввода. [spaCy](https://spacy.io/usage/linguistic-features) описывает доступные аннотации. [OpenDial](https://sites.google.com/site/opendialtoolkit/user-manual/step-by-step-example) демонстрирует выбор уточнения на основе состояния/неопределённости, но сам не является нашим немецким парсером. [PICARD](https://aclanthology.org/2021.emnlp-main.779/) ограничивает допустимую форму вывода модели; это не доказательство семантической правильности вывода.

## Как проверить решение без очередной подгонки

Ограниченный словарь уменьшает задачу, но не делает перебор всех строк разумным: уже 183^6 ≈ 3,76×10^13 последовательностей. Генерировать нужно **из смысловых структур и грамматических семейств**: менять роли, полярность, модальность, порядок, формы и разрешённые пропуски. Сохранять дерево происхождения каждого примера.

Однако генератор и парсер с одной грамматикой могут согласованно ошибаться. Поэтому обязательны независимые семантические контрасты, свободные вводы человека и отдельные замороженные семейства для итогового контроля. Косметические изменения имени/регистра не считать независимым обобщением. Исторический oracle не менять ради нового процента.

Рекомендуемый следующий шаг — ограниченный сравнительный прототип трёх семейств: просьба/владение документом; утверждение/отрицание роли; направление помощи/передачи. Работать через единый интерфейс, параллельно нынешнему runtime, без переключения gameplay до проверки. Проверка принятия:

- Все проверки текущего продукта вызывают именно production entry point; старый корпус имеет явный адаптер и пометку домена.
- На однозначных контрастах сохраняются участники, полярность, модальность и речевой акт; на неоднозначных — конкретное уточнение без эффекта.
- Отрицание, неизвестное условие, противоречие и незавершённая самопоправка не исчезают из смысловой структуры.
- Пропущенный объект восстанавливается в подходящем контексте, а при двух подходящих объектах NPC различает их вопросом.
- Новое совместимое существительное/прилагательное добавляется в данные без изменения функций разбора; проверяется также на сочетаниях, которых не было среди примеров разработки.
- Проверяются полные диалоги через Session/Composer: уточнение → Ja/Nein → однократный эффект; смена мысли, закрытие, reset и устаревшее уточнение.
- Измеряются отдельно ложные действия, ошибки ролей/отрицания, ложные отказы, качество уточнений и полнота покрытия значимых токенов. Число зелёных примеров само по себе критерием не служит.
- Нельзя объявлять приёмку при сломанном runner, обходе нового анализатора или провале отложенной проверки.

Это проверяемый путь к улучшению, а не обещание полного человеческого понимания. Остаточное авторство остаётся на уровне новых слов, семантических типов, конструкций и сценарных фактов; ручное условие на каждую очередную реплику игрока не должно быть штатным способом разработки.

## Воспроизведение

Из корня проекта, установленным console Godot:

```powershell
Godot_v4.7.1-stable_win64_console.exe --headless --path . --script res://implementations/communication_lab/experiments/audit_runtime_parser.gd --quit-after 600
```

При необходимости направить `APPDATA` в ignored `.local/godot-appdata`, как в остальных проверках этого расследования. Скрипт записывает наблюдения в `.local/parser-audit-results.json`; он не читает corpus expected/validation. Таблицы выше фиксируют исследованную ревизию, а не обещают те же результаты после будущих изменений.
